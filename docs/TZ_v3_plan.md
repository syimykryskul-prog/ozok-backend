# OZOK — сведение с ТЗ NBS: недостающие функции и решения (v3)

Дата: 15.11.2026. Источник требований — `docs/TZ_NBS.md` (ТЗ ОсОО «НБС Холдинг»). **Где ТЗ NBS расходится с `docs/TZ.md` (разделы 1–12, 5А–5Д), прав ТЗ NBS.** Этот документ фиксирует, ЧТО добавить и КАК встроить в существующую систему (Django + DRF / React + RTK Query / Flutter). Пакеты упорядочены по этапам ТЗ NBS (§19): сначала всё для MVP-приёмки (§20).

**ОБЯЗАТЕЛЬНО прочитать `docs/TZ_v3_decisions.md`** — проектные решения после ревью (валюты, распределение платежей по начислениям, $150 рекрутеру, единый источник оплат, получатель комиссии на дату оплаты, изоляция по филиалам, двухшаговый расчёт ставки и т.д.). Они приоритетнее текста этого плана.

Общие правила для всех пакетов:
- Название системы в интерфейсе — **OZOK**, владелец — **NBS** («НБС Холдинг»). Слово «центр» в интерфейсе заменить на «NBS».
- Не ломать существующий API-контракт без необходимости; новые поля — добавлять. Если поле переименовывается — миграция данных + обновление web/mobile.
- **Финансовые данные не удаляются физически** (§18): Charge, FranchiseePayment, CommissionPayout, ClientSale, CommissionAccrual, RecruiterReward, Payment — только `cancel/archive` с `cancel_reason`, `cancelled_by`, `cancelled_at`. Существующие DELETE для этих ресурсов → заменить на действие `cancel/`.
- Каждое изменение денег, цен, договоров, статусов, комиссий, выплат, ролей пишется в **журнал аудита** (P1).
- Деньги: `Decimal`, строки в JSON. **Только сомы (KGS)** — решение заказчика: никаких USD и курсов; в P3 и P0 всё, что касается валют и `ExchangeRate`, не делать. Суммы в долларах из ТЗ NBS ($1 000, $2 000, $150) — настраиваемые суммы в сомах (по умолчанию 87 500 / 175 000 / 13 125).

## P0. Всё настраивается вручную в программе (решение заказчика 15.11.2026)

Заказчик: **все ставки, цены, сроки и условия NBS задаёт и меняет сама в разделе «Настройки» программы** — ничего не зашивается в код. Значения ниже — только начальные (сидер), каждое редактируется в интерфейсе (super_admin; финансовые — также finance), каждое изменение пишется в журнал аудита с причиной, а ставки/цены — с датой начала действия (прошлые расчёты не меняются).

**Решение по лидам из рекламы NBS (ответ на §21.1):** если лид пришёл из рекламы NBS (`lead_source = nbs_ads`):
- франчайзи получает **15% абонентской платы** (вместо обычных 20%/30%);
- франчайзи **отдаёт NBS 30% от дохода, полученного от клиента** (установка, обучение, оборудование, прочее) — т.е. оставляет себе 70%. Эти деньги находятся у франчайзи, поэтому доля NBS оформляется как начисление франчайзи `Charge(kind=nbs_lead_share)` со сроком оплаты (по умолчанию дата продажи + 30 дней, срок — настройка) и видна в его Расчётах как «Доля NBS по лидам NBS».
- Реализация — через правила `CommissionRule` с областью `lead_source=nbs_ads`: «Лид NBS — абонплата — 15%», «Лид NBS — установка/обучение/оборудование/прочее — доля франчайзи 70% (NBS 30%)». В интерфейсе правила для видов дохода, где деньги у франчайзи, показываются как «Доля NBS, %» (= 100 − доля франчайзи). Ставки по продуктам и типу партнёра (Standard/Growth) задаются отдельными правилами при необходимости.

**Раздел «Настройки» (web, super_admin; вкладки):**
1. **Продукты и тарифы** — продукты, тарифы, история цен «с даты», `setup_price`, `training_price`, `min_price`, `max_discount_percent`, льготный период и ограничение доступа (`grace_days`, `restrict_after_days`) на продукт и с переопределением на тариф, чек-лист установки продукта, распределение оплаты установки (`SetupSplitRule`, напр. OnAI 20 000 = 12 000 + 8 000).
2. **Оборудование** — модели, закупочная/продажная цена, гарантия.
3. **Комиссии и доли** — все `CommissionRule` (Standard/Growth по продуктам, лиды NBS 15% / 30%, индивидуальные условия партнёров) с калькулятором-превью.
4. **Франшиза** — предложения (`FranchiseOffer`: «Сразу $1 000», «Рассрочка до $2 000», шаги), процент удержания из дохода по умолчанию, вознаграждение рекрутера (сумма, по умолчанию $150, валюта).
5. **Курсы валют** — курс USD/KGS на дату (вводит финансист; кнопка «Взять курс НБКР» — позже).
6. **Сроки и SLA** — срок ответа по второму филиалу (по умолчанию 3 дня), SLA обращений по приоритету и уровню L1/L2/L3, срок оплаты доли NBS и удержаний, напоминания об оплате подписки (за N дней до и через N дней после), просрочка заявки (часы), порог нарушений SLA для ограничения на новые филиалы.
7. **Growth** — условия по умолчанию (бюджет/мес, публикаций/мес, лидов/мес, период проверки), веса блоков рейтинга.
8. **Согласования** — кто одобряет скидки ниже минимума и изменения лидов (роли).
9. **Уведомления** — включение событий и каналов (в системе, e-mail, Telegram), шаблоны текстов.
10. **Интеграции** — ключи продуктов, Элкюар (секрет вебхука), SMTP, Telegram-бот (секреты хранятся зашифрованно, на фронт не отдаются).
11. **Пользователи и роли**.

Хранение простых параметров — модель `SystemSetting` (key, value JSON, type, label, group, updated_by, updated_at) + история в аудите; ресурс `settings/` (GET — все авторизованные читают нужные им ключи; PATCH — super_admin, финансовые ключи — finance). Сложные сущности (тарифы, правила, оборудование, предложения франшизы) — свои ресурсы. Код читает параметры только через `get_setting(key)` с кэшем, никаких констант в коде.

## P0+. Продажи одной формой, продажи NBS, доходы/расходы партнёров, аналитика (решение заказчика 16.11.2026)

**1. Каждую продажу вносит тот, кто продал.** Франчайзи (и менеджер-партнёр) вносит каждую новую продажу в своём кабинете. **NBS тоже вносит свои прямые продажи** — продажа без партнёра (`partner = null`, «Продажа NBS»), доход целиком NBS, комиссий нет. Продажи NBS видны в аналитике отдельной строкой «NBS (прямые продажи)».

**2. Одна продажа = одна форма со всеми видами сразу.** Модель `Deal` (= ClientDeal из P6, делать сейчас): client (+ branch, когда появится P5), partner (nullable = NBS), lead (nullable), product (сфера), date, status (`draft|pending_approval|confirmed|cancelled`), comment, created_by, totals (вычисляемые: list_total, discount_total, total, partner_income_total, nbs_income_total).
**DealLine** (строки продажи, в одной продаже — любые сочетания):
- `setup` — установка и обучение (одна строка; цена по прайсу продукта, при необходимости отдельной строкой `training`);
- `equipment` — оборудование (несколько строк: модель из справочника, количество, цена за единицу, серийные номера);
- `subscription` — абонентская плата: тариф, количество месяцев, цена в месяц по прайсу на дату.
У каждой строки: `list_price` (из прайса на дату, снимок), `quantity`/`months`, `discount_percent` **или** `discount_amount`, `discount_reason`, `total` = list − скидка. Плюс общая скидка на всю продажу (`deal_discount_percent/amount`, распределяется по строкам пропорционально).
**Скидка:** если по строке цена ниже минимальной или скидка выше допустимой (Настройки) → продажа уходит в `pending_approval`, создаётся ChangeRequest; NBS одобряет/отклоняет; всё в аудите.
**Подтверждение продажи** (`confirm`) создаёт по строкам записи дохода (`ClientSale` setup/equipment, а для абонплаты — подписку/ожидаемую оплату; фактическая абонентская оплата и комиссия начисляются только при поступлении денег — P8/P9). Доход партнёра и доля NBS по каждой строке считаются по правилам (CommissionRule, лиды NBS, удержание в счёт франшизы) и показываются в форме **до сохранения** (превью).
Форма в вебе и мобилке: клиент (поиск или «новый клиент» прямо в форме) → сфера → блоки «Установка и обучение», «Оборудование» (+ добавить строку), «Абонплата» (тариф, месяцы) — каждый блок можно включить/выключить → скидки → итог: «Сумма по прайсу, Скидка, К оплате, Ваш доход, Доля NBS / удержание».

**3. Доходы и расходы партнёра.** Франчайзи ведёт в кабинете учёт своих **доходов и расходов**:
- **PartnerLedgerEntry**: partner, date, type (`income|expense`), category, amount, description, product (сфера, nullable), attachments (чек/подтверждение, P12), created_by, cancelled (cancel с причиной, без удаления).
- Категории — справочник в Настройках (`LedgerCategory`: type, name, is_active): расходы по умолчанию — Аренда, Зарплата, Реклама/маркетинг, Транспорт, Закупка оборудования, Связь и интернет, Налоги, Прочее; доходы — Прочий доход (доходы от продаж подтягиваются **автоматически** из продаж, вручную их не вводят).
- Отчёт партнёра «Доходы и расходы» за период: доходы от продаж (по видам и сферам) + прочие доходы − расходы (по категориям) − доля NBS/удержания = **прибыль партнёра**; график по месяцам.
- Рекламные расходы (категория «Реклама/маркетинг») идут в блок «Маркетинг» рейтинга и в Growth-проверку (P10).
- NBS видит доходы/расходы всех партнёров; партнёр — только свои.

**4. Аналитика.**
- **Карточка партнёра → вкладка «Аналитика»**: всё по этому партнёру за период с разбивкой **по каждой сфере** — продажи (количество, суммы по видам: установка/оборудование/абонплата), скидки, лиды и конверсия по этапам, клиенты и филиалы, активные/просроченные подписки, собранная абонплата, начисленная/выплаченная комиссия, удержания, доля NBS, доходы/расходы/прибыль партнёра, качество (SLA, жалобы, оценки), рейтинг; динамика по месяцам; сравнение со средним по сети.
- **Раздел «Аналитика» NBS**: переключатель «Вся сеть / По сфере / По партнёру»:
  - по сфере — таблица успеваемости **всех партнёров в этой сфере** (продажи, выручка, абонплата, подписки, конверсия, средний чек, скидки, просрочка, рейтинг, место в сфере), топ и отстающие, динамика;
  - вся сеть — свод по сферам и по партнёрам, доля прямых продаж NBS;
  - фильтры: период, регион, статус партнёра (Standard/Growth/менеджер), источник лида; экспорт Excel.
- API: `reports/partner-analytics/?partner=&date_from=&date_to=` (по сферам), `reports/sphere-analytics/?product=&date_from=&date_to=` (по партнёрам сферы), `reports/ledger/?partner=&date_from=&date_to=`; партнёр получает только свои данные.

**5. Дашборд и аналитика — один экран (решение заказчика 16.11.2026).** Пункты меню «Дашборд сети» и «Аналитика» объединяются в один — **«Дашборд и аналитика»** (`/`; старый `/analytics` редиректит сюда с теми же параметрами).
- Сверху — общая панель фильтров: период (месяц / квартал / произвольный), переключатель **«Вся сеть / По сфере / По партнёру»**, регион, статус партнёра (Standard/Growth/менеджер), источник лида. Фильтры хранятся в URL (можно поделиться ссылкой).
- **Вся сеть**: тёмный hero с главными цифрами (активные франчайзи, выручка, собранная абонплата, долг сети), KPI-карточки текущего дашборда, блок «Требует внимания», затем аналитика: свод по сферам (карточки сфер с выручкой, абонплатой, подписками, комиссией), рейтинг партнёров, динамика по месяцам, доля прямых продаж NBS.
- **По сфере**: hero по выбранной сфере + таблица успеваемости всех партнёров в сфере (место, продажи, выручка, абонплата, подписки, конверсия, средний чек, скидки, просрочка, рейтинг), топ/отстающие, динамика.
- **По партнёру**: hero по партнёру + всё по нему по каждой сфере (то же, что вкладка «Аналитика» в карточке партнёра — один и тот же компонент).
- Партнёр (франчайзи/менеджер) видит тот же экран «Мой дашборд и аналитика» только по себе: свои KPI, план, рейтинг и место, свои сферы, доходы/расходы, сравнение со средним по сети.
- Данные: `dashboard/` (KPI и «Требует внимания» за период) + `reports/partner-analytics/`, `reports/sphere-analytics/`, `reports/sales/`, `reports/rating/`. Компоненты не дублировать.

**6. «Касса» — все деньги в одном разделе (решение заказчика 16.11.2026).** Разделы «Расчёты», выплаты, платежи и т.п. объединяются в один пункт меню **«Касса»**. Всё, что связано с деньгами, — там.

Backend:
- **CashAccount** (счёт/касса NBS): name («Наличная касса», «Банк Элдик», «Элкюар»), kind (`cash|bank|elqr`), is_active, opening_balance, opening_date. Остаток = opening + Σ поступлений − Σ выплат.
- **CashTransaction** — единый журнал движения денег NBS: date, account, direction (`in|out|transfer`), amount, category (справочник `CashCategory`, настраивается в Настройках; поступления: «Абонплата клиентов», «Взносы за франшизу», «Прямые продажи NBS», «Доля NBS по лидам NBS», «Удержания с продаж», «Прочие поступления»; расходы: «Выплаты комиссий франчайзи», «Вознаграждения рекрутерам», «Оплата внедренцам», «Аренда», «Зарплата», «Реклама NBS», «Закупка оборудования», «Налоги», «Прочие расходы»), partner (nullable), client (nullable), source_type + source_id (ссылка на Payment / FranchiseePayment / Payout / RecruiterReward / ImplementerAccrual / Deal / NbsExpense), comment, attachments, created_by, cancel-only.
- **Проводки создаются автоматически** при каждом денежном событии: подтверждённая абонентская оплата (in), платёж франчайзи по франшизе/доле NBS/удержанию (in), оплаченная прямая продажа NBS (in), проведённая выплата комиссии / рекрутеру / внедренцу (out). Отмена события → сторнирующая проводка. Вручную — только прочие поступления, расходы NBS и переводы между счетами (finance, super_admin).
- **NbsExpense** = ручная проводка `out` с категорией расхода и вложением (чек/счёт).
- Ресурсы: `cash-accounts/`, `cash-transactions/` (фильтры account, direction, category, partner, date_from, date_to; `cancel/`), `cash-categories/`, `reports/cash/?date_from=&date_to=` → остатки по счетам на начало/конец, поступления и расходы по категориям, по месяцам, cash-flow; экспорт Excel.

Web — пункт меню **«Касса»** (NBS: super_admin, finance; network_head — чтение) с вкладками:
1. **Обзор** — остатки по счетам, поступило / потрачено / чистый поток за период, график по месяцам, ближайшие ожидаемые поступления (рассрочки франчайзи, подписки к оплате) и ожидающие выплаты.
2. **Поступления** — все входящие: абонплата клиентов, взносы франчайзи, прямые продажи NBS, доля NBS, прочее (+ «Добавить поступление»).
3. **Расходы NBS** — расходы с категориями и чеками (+ «Добавить расход»), перевод между счетами.
4. **Выплаты** — очередь: комиссии франчайзи, вознаграждения рекрутерам, оплата внедренцам — статусы «к проверке → проверено → выплачено» (проверяет и выплачивает разные сотрудники).
5. **Расчёты с партнёрами** — по каждому партнёру: должен NBS (взнос, рассрочка, доля NBS, удержания, просрочка) и NBS должен ему (комиссии к выплате); начисления, платежи, прогресс погашения франшизы.
6. **Сверка** — импорт банковской выписки, нераспознанные платежи.
Для партнёра пункт **«Касса»** = его «Доходы и расходы» + «Расчёты с NBS» + «Мои комиссии» в одном разделе (вкладки: Обзор, Доходы и расходы, Расчёты с NBS, Комиссии и выплаты).

**7. Боковое меню — максимально понятное.** Группы с заголовками, простые слова, иконки, счётчики-бейджи (сколько ждёт действия), сворачиваемые группы, активный пункт подсвечен; не больше ~15 пунктов у NBS и ~10 у партнёра; пункты, на которые у роли нет прав, не показываются.

NBS (super_admin):
- **Главное:** Дашборд и аналитика
- **Продажи:** Лиды · Продажи · Клиенты и филиалы · Установки
- **Деньги:** Касса
- **Партнёры:** Кандидаты · Партнёры · Рекрутеры · Договоры франшизы
- **Работа и качество:** Задачи · Обращения и качество · Обучение · Планы и рейтинг
- **Система:** Согласования (бейдж — сколько ждут) · Интеграции · Журнал аудита · Настройки
- внизу: профиль, 2FA, выход.

Партнёр (франчайзи/менеджер):
- Мой дашборд · Лиды · Продажи · Клиенты · Установки · **Касса** · Задачи · Обращения · Обучение · Мои условия и сферы · Команда (только владелец).

Остальные роли (рекрутер, техподдержка, внедренец, контроль качества, финансист) — только свои пункты, первым — их рабочий экран (финансист → Касса).

**8. Владелец сам выдаёт доступ сотрудникам (решение заказчика 16.11.2026).** Права больше не зашиты в код — владелец (super_admin) управляет ими в «Настройки → Сотрудники и доступ».

Backend:
- **AccessRole** (роль доступа): name, description, is_system (системные роли из ТЗ NBS §3 — сидер, их можно редактировать, но не удалять), `permissions` (JSON-матрица: модуль → уровень `none|read|write`), `actions` (список особых прав), `scope` (`all` | `own_region` | `own_partners` (привлечённые/закреплённые) | `assigned` (назначенные ему установки/лиды)).
- **Модули матрицы** (= разделы меню): dashboard, leads, sales (продажи/сделки), clients (клиенты, филиалы, подписки), installations, cash (касса), cash_partners (расчёты с партнёрами), payouts, candidates, partners, recruiters, franchise_contracts, tasks, quality (обращения, проверки, Growth), training, plans_rating, approvals, integrations, audit_log, settings, users.
- **Особые права (actions)**: `approve_discounts`, `approve_lead_changes`, `verify_payouts`, `pay_payouts`, `view_personal_data` (паспорт/ИНН), `export`, `change_prices_rules`, `manage_partner_status` (Standard/Growth, приостановка, закрытие), `cancel_financial`, `manage_users`.
- **User**: `access_role` (FK AccessRole), `permission_overrides` (JSON — индивидуальные отличия от роли: модуль→уровень, ±actions), `scope_region`, `must_change_password`, `invited_by`, `last_login`, is_active. Итоговые права = роль + индивидуальные отличия. Существующие коды ролей (super_admin, finance, …) мигрируют в AccessRole с такими же правами, как сейчас в `core/permissions.py`; проверка прав в API читает итоговые права из БД (с кэшем на запрос), а не из константы.
- Владелец (super_admin) всегда имеет все права; последнего super_admin нельзя отключить или понизить.
- Партнёрские роли (franchisee, franchisee_staff, manager) остаются привязанными к своему партнёру; **владелец франчайзи** тоже может выдавать доступ **своим** сотрудникам, но только в пределах партнёрских модулей и не больше своих прав.
- API: `access-roles/` (CRUD, `duplicate/`), `users/` (+ `invite/` — создаёт пользователя с временным паролем и флагом must_change_password, `deactivate/`, `activate/`, `reset-password/`, `effective-permissions/`), `auth/change-password/`. Все изменения ролей и прав — в журнал аудита. `auth/me/` возвращает итоговые `permissions` и `actions` — фронтенд строит меню и кнопки только по ним.

Web — «Настройки → Сотрудники и доступ»:
- Список сотрудников: имя, e-mail, роль, регион, статус, последний вход; «Пригласить сотрудника» (имя, e-mail, телефон, роль, регион → показывается временный пароль, который владелец передаёт сотруднику); отключить/включить; сбросить пароль.
- Карточка сотрудника: роль + **таблица прав по разделам** (переключатель «Нет / Просмотр / Изменение» для каждого раздела) + галочки особых прав + область видимости (все / свой регион / свои партнёры / только назначенное); отличия от роли подсвечены, кнопка «Вернуть как в роли»; история изменений прав.
- Роли доступа: список, создать свою роль («Копировать из…»), редактировать матрицу.
- При первом входе с временным паролем — экран смены пароля.
- Меню и кнопки во всём приложении показываются только по итоговым правам из `auth/me/`.

**9. Существующие клиенты OZOK (решение заказчика 16.11.2026).** У OZOK уже есть клиенты, которые пользуются продуктами и платят абонплату **100% OZOK** (без франчайзи). Их нужно завести в систему по сферам.

Backend:
- `Client.origin`: `partner` (привёл партнёр, по умолчанию) | `ozok_legacy` (существующий клиент OZOK) | `ozok_direct` (новая прямая продажа OZOK). Для `ozok_legacy` у филиалов seller/implementer = null; абонплата 100% OZOK, **комиссия не начисляется** никому.
- Если позже OZOK передаёт такого клиента франчайзи на **сопровождение** (через существующее переназначение филиала с причиной), комиссия по нему по-прежнему **не начисляется**, пока OZOK явно не включит её для этого филиала (`Branch.commission_enabled`, по умолчанию `false` для legacy, меняет только super_admin, с аудитом и датой начала). Ставку, если включена, — по обычным правилам.
- Для каждой сферы (продукта) у клиента/филиала: подписка с тарифом (или своей ценой `monthly_price`), `started_at` (с какого числа пользуется), `paid_until` (до какого числа оплачено), статус считается автоматически, `external_id` — ID клиента в самом продукте (для сопоставления будущих оплат из интеграции), лицевой счёт Элкюар.
- **Добавление по одному**: `POST clients/legacy/` — компания, ИНН, контакт, телефон, город/регион, адрес филиала, и список сфер `[{product, tariff | monthly_price, started_at, paid_until, external_id, elqr_account}]`.
- **Массовый импорт по сфере**: `POST clients/legacy-import/preview/` (CSV/XLSX — шаблон по сфере, скачивается `GET clients/legacy-import/template/?product=`), колонки: название, ИНН, контакт, телефон, город, адрес, тариф (код или название), цена в месяц, пользуется с, оплачено до, ID в продукте, лицевой счёт Элкюар. Предпросмотр: новые / дубли (по ИНН, телефону, ID в продукте, лицевому счёту) / ошибки по строкам; затем `POST clients/legacy-import/confirm/`. Дубли можно «объединить с существующим» (добавить сферу существующему клиенту) или пропустить. Только super_admin и finance (и кому выдано право).
- Прошлые оплаты таких клиентов не нужно вводить; при желании — через обычный ручной ввод/импорт оплат (они идут 100% OZOK, без комиссии).
- Отчёты/аналитика: отдельный сегмент **«Собственные клиенты OZOK»** (legacy + direct) — количество, подписки по статусам, MRR и собранная абонплата по сферам; в «Вся сеть» — доля OZOK vs партнёров.

Web — «Клиенты и филиалы» → кнопка **«Добавить существующих клиентов»**:
- вкладка «По одному»: форма компании + блоки сфер (добавить сферу: продукт, тариф/цена, пользуется с, оплачено до, ID в продукте, лицевой счёт);
- вкладка «Импорт по сфере»: выбрать сферу → скачать шаблон → загрузить файл → предпросмотр с цветами (новые / дубли / ошибки, действие для дублей) → «Импортировать N клиентов»;
- в списке клиентов фильтр «Источник: Партнёр / Клиент OZOK (существующий) / Прямая продажа OZOK» и метка у клиента;
- в карточке филиала legacy-клиента — переключатель «Начислять комиссию сопровождающему партнёру» (только владелец).

- `User.region` (для regional_support), `User.partner` (FK Partner — для franchisee/franchisee_staff/manager).
- Таблица прав `core/permissions.py` переписывается под эти роли; тесты изоляции — на каждую роль.

**Партнёр** — переименовать смысл модели `Franchisee` в «Партнёр» (модель можно оставить `Franchisee`, в API добавить алиас не нужно — просто расширить):

- **Статус партнёра** (`status`): `candidate`, `trainee`, `manager`, `franchisee` (Standard/Growth задаётся `tier`), `suspended`, `closed`. Миграция: candidate→candidate, onboarding→trainee, active→franchisee, suspended→suspended, terminated→closed.
- **История статусов и tier**: модель `PartnerStatusHistory` (partner, field `status|tier`, old, new, effective_from, reason, decided_by, created_at). Tier применяется **с даты** `effective_from` (по умолчанию — 1-е число следующего расчётного месяца при понижении); задним числом — только super_admin с обязательной причиной (аудит).
- Абонентская комиссия начисляется **только** если на дату оплаты статус партнёра `franchisee`. Для `candidate/trainee/manager/suspended/closed` — 0 (с пометкой причины в начислении).

**Журнал аудита** — модель `AuditLog`: user, action (`create|update|cancel|status|login|login_failed|export|approve|reject`), entity (строка «app.Model»), entity_id, changes (JSON `{field: [old, new]}`), reason, ip, user_agent, created_at. Пишется сигналами/миксином для всех финансовых моделей, цен, тарифов, правил комиссии, договоров, статусов партнёров, ролей пользователей, лидов (источник/цена/ответственный), а также вход/неудачный вход. Ресурс `audit-log/` (super_admin, finance; фильтры entity, entity_id, user, action, date_from/to). В карточках сущностей — вкладка «История изменений».

**2FA** (§18): TOTP для ролей super_admin и finance (pyotp). `auth/login/` при включённой 2FA возвращает `{"otp_required": true, "otp_token": "..."}`, затем `POST auth/login/otp/ {otp_token, code}` → токены. Настройка: `auth/2fa/setup/` (QR-ссылка otpauth), `auth/2fa/enable/ {code}`, `auth/2fa/disable/ {code}`. Throttle на логин 5/мин.

## P3. Франшиза в USD, рассрочка, выплата рекрутеру $150 (MVP §19.4–5, §20.2–3)

- `Contract.currency` (`KGS`|`USD`, по умолчанию USD для франшизы). Все суммы договора и начисления/платежи по нему — в валюте договора. Отчёты в KGS считаются по курсу на дату платежа.
- **Курсы**: модель `ExchangeRate` (currency, rate_to_kgs, date, source `manual|nbkr`, set_by). Ресурс `exchange-rates/` (finance, super_admin пишут; все читают). Курс на дату = последний с date ≤ даты.
- Пресеты договора франшизы (§20.2): «Сразу $1 000» и «Рассрочка до $2 000» — значения по умолчанию задаются в настройках (`FranchiseOffer`: name, currency, total, upfront, installments_count, step_months, is_active). Гибридный конструктор из 5Д сохраняется.
- **RecruiterReward**: partner (unique), recruiter, target_amount (по умолчанию 150 USD — настройка), currency USD, accrued_amount, status (`accruing|accrued|verified|paid|cancelled`), verified_by/at, paid_by/at, payout_rate (курс на дату выплаты), payout_kgs.
  - При каждом **подтверждённом** платеже партнёра по договору франшизы (FranchiseePayment, кроме offset-удержаний из продаж — уточнение: удержания из продаж тоже являются деньгами, полученными NBS, поэтому **учитываются**) — первые деньги идут в `accrued_amount` до target. Аллокация хранится: `RecruiterRewardAllocation` (reward, payment, amount_usd).
  - Достигли target → `accrued`. Финансист проверяет → `verified` → проводит выплату → `paid` (с курсом и суммой в сомах). Отмена платежа партнёра уменьшает accrued (если ещё не paid; если paid — создаётся корректировка-долг рекрутера, видна финансисту).
  - Рекрутер видит своих кандидатов/партнёров, этапы, платежи партнёра (только суммы и даты), остаток до $150 и статус выплаты.
- Отчёт рекрутеров: привлечено, активировано, начислено, выплачено (§16).

У каждого клиента минимум один филиал; существующие ClientProductAccount → привязать к филиалу (миграция: создать основной филиал на клиента).
- **ClientContact**: client, branch (nullable), full_name, position, phone, email, is_primary.
- **Подписка** — `Subscription` на **филиал** (переиспользовать/переименовать ClientProductAccount): branch, product, tariff, monthly_price (с учётом скидки), status (`awaiting_payment|active|grace|overdue|restricted|closed`, §10.3), paid_until, started_at, closed_at. Статус пересчитывается ежедневно командой `update_subscription_statuses` и при каждой оплате: `paid_until ≥ сегодня` → active; в пределах `grace_days` → grace; дольше → overdue; дольше `restrict_after_days` → restricted. `grace_days` и `restrict_after_days` — в `Product` и переопределяются в `Tariff` (§21.6). Изменение статуса → событие в продукт (P9) и уведомление (P11).
- **Комиссия по филиалу**: начисление привязано к branch; получатель — `implementer_partner` филиала **если он же сопровождает** (responsible_partner) и статус партнёра franchisee; иначе — правило ниже.
- **Правило второго филиала** (§7.2): при создании нового филиала у клиента, у которого уже есть филиал с partner X, филиал создаётся с `priority_partner = X` и `priority_deadline = now + N дней` (N — настройка `SECOND_BRANCH_RESPONSE_DAYS`, по умолчанию 3). Партнёр X получает уведомление; может «Принять» (`POST branches/{id}/accept/`). Если не принял до дедлайна или NBS решила переназначить по основанию (`no_response|no_crm_activity|install_overdue|confirmed_complaint|other` + текст) — `POST branches/{id}/reassign/ {partner, reason_code, reason}`; запись `BranchAssignmentHistory` (branch, from_partner, to_partner, reason_code, reason, decided_by, created_at). Комиссия по филиалу начисляется только тому, кто внедрил после официального назначения; исходному — нет.
- **Уход франчайзи** (§7.3): `POST partners/{id}/close/ {closed_at, reason, transfer_to_partner | transfer_to_user}` в одной транзакции: статус closed; все `User` партнёра — `is_active=false` (доступ блокируется, refresh-токены отзываются); клиенты/филиалы/открытые обращения/лиды → новому ответственному (история в BranchAssignmentHistory/LeadActivity); начисления по оплатам с датой > closed_at этому партнёру не создаются (уходят новому ответственному по правилам или NBS); уведомление клиенту (P11, e-mail контакту) «ваш новый ответственный — …». Отчёт «Передачи клиентов».
- **ChangeRequest** (универсальный запрос на подтверждение NBS): requested_by, entity, entity_id, field, old_value, new_value, reason, status (`pending|approved|rejected`), decided_by/at, decision_comment. Используется для: изменения источника/ответственного лида, скидки ниже минимума (P6), цены. `change-requests/` + `approve/`, `reject/`.

## P6. Продажи, договоры клиентов, цены, скидки, согласование (MVP §19.3, §8)

- **Прайс-лист на дату**: у Tariff уже есть TariffPrice (история). Добавить в Product/Tariff: `setup_price`, `training_price` (отдельно от установки), `min_price` (минимальная цена тарифа в месяц) и `max_discount_percent`. Изменения цен — только через «с даты», в аудите.
- **ClientDeal** (продажа/договор с клиентом — не путать с ClientSale-начислением): client, branch, partner (продавец), lead (nullable), product, tariff, `price_list_snapshot` (JSON: цены тарифа/установки/обучения на дату), `subscription_price` (договорная/мес), `setup_price`, `training_price`, `equipment_total`, `discount_percent`, `discount_amount`, `discount_reason`, `discount_approved_by/at`, `contract_number`, `signed_at`, `contract_file` (P12), `payment_status` (`unpaid|partial|paid`), status (`draft|pending_approval|approved|signed|paid|cancelled`).
- **Согласование**: если цена ниже `min_price` или скидка > `max_discount_percent` → статус `pending_approval`, создаётся ChangeRequest; без одобрения NBS договор нельзя перевести в `signed`. Одобряют super_admin/network_head (настраивается).
- Оплата договора клиента (установка/обучение/оборудование) — фиксируется как ClientSale видов setup/training/equipment, привязанных к deal; при `paid` → создаётся Installation (P7).
- Шаблоны договоров (`ContractTemplate`: kind `manager|franchisee|client`, name, file, is_active) — хранение файлов (P12).

## P7. Установки и обучение, OnAI CRM, оборудование (MVP-часть; этап 2 — логистика)

- **Installation** (расширить Implementation): deal, branch, product, `implementer` (FK User — внедренец/разработчик), `partner` (франчайзи/менеджер), deadline, status (`assigned|in_progress|training|awaiting_act|done|cancelled`), `checklist` (JSON по шаблону продукта: `[{item, done, done_at, comment}]`), `training_result` (`passed|needs_repeat`), `client_rating` (1–5), `act_file`, `act_confirmed_at`, `client_confirmed_by` (имя), comments (InstallationComment), attachments (P12). Процесс §9.1: при `done` + подтверждение клиента → подписка филиала переходит из `awaiting_payment` и (если оплачено) в `active`.
- `ChecklistTemplate` (product, items[]) — редактирует super_admin.
- **Распределение дохода за установку** (`SetupSplitRule`): product, total (например 20 000), доли: `partner_amount` (12 000), `implementer_amount` (8 000), `implementer_condition` (`channels_connected_and_confirmed`). Для OnAI CRM: `technical_channels` (JSON список: `whatsapp`, `instagram`, `facebook`, `api_telephony` + статус `pending|connected|failed`), `technical_status`. Начисление внедренцу (`ImplementerAccrual`: installation, user, amount, status `pending|accrued|verified|paid`) создаётся **только** когда все каналы `connected` и акт подтверждён клиентом. Сидер: OnAI — 20 000 = 12 000 + 8 000.
- **Оборудование** (расширить Equipment + новая EquipmentSale): Equipment: model, `purchase_price`, `sale_price`, `margin` (вычисляемое), `warranty_months`. EquipmentSale (= ClientSale kind equipment + детали): equipment, quantity, `serial_numbers` (JSON), `sold_by` (partner), `installed_by` (user/partner), `delivery_status` (`ordered|in_stock|delivered|installed`), `warranty_until`.
- **Менеджер** (статус партнёра manager) получает доход от установки/обучения/оборудования по тем же правилам, абонентской комиссии — 0.
